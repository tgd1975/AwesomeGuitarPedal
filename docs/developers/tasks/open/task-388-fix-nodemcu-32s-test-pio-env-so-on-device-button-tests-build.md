## Description

The `nodemcu-32s-test` PlatformIO environment (and its on-device test
siblings) cannot build today. `make test-esp32-button` aborts in the
compile stage on a clean `main` checkout with two distinct errors:

1. **Missing header on the include path.**

   ```text
   src/esp32/include/button.h:2:10: fatal error: i_button.h: No such file or directory
    #include "i_button.h"
             ^~~~~~~~~~~~
   compilation terminated.
   *** [.pio/build/nodemcu-32s-test/test/test_buttons_esp32/test_main.cpp.o] Error 1
   ```

   `i_button.h` lives at [`lib/PedalLogic/include/i_button.h`](../../../../lib/PedalLogic/include/i_button.h).
   The production env (`nodemcu-32s`) resolves it fine through PlatformIO's
   Library Dependency Finder; the test env does not. The two envs differ
   in `build_src_filter` and `build_flags` but not in `lib_deps`/`lib_ldf_mode`,
   so the regression is in how the test env walks `lib/PedalLogic/`.

2. **`FakeSerial` shadows the real `HardwareSerial` and breaks Unity's
   serial output config.**

   ```text
   unity_config.cpp:39:47: error: 'struct FakeSerial' has no member named 'write'
   unity_config.cpp:40:38: error: 'struct FakeSerial' has no member named 'flush'
   unity_config.cpp:41:41: error: 'struct FakeSerial' has no member named 'end'
   ```

   The test env's `build_flags` includes `-Itest/fakes`, which puts the
   host-test [`arduino_shim.h`](../../../../test/fakes/arduino_shim.h)
   on the include path. `FakeSerial` declares no `write`/`flush`/`end`
   methods, so PlatformIO's autogenerated `unity_config.cpp` fails to
   compile inside the on-device test build. The fakes belong to the
   host (`make test-host`) build only.

Both failures predate the `feature/firmware` branch and reproduce on
`main` (verified by checking out the relevant files from `main` and
re-running the test build). EPIC-028 / TASK-376 closed with on-device
verification done by flashing production firmware rather than running
the Unity test suite — the new debounce scenarios are written and
ready to run in [`test/test_buttons_esp32/test_main.cpp`](../../../../test/test_buttons_esp32/test_main.cpp)
once this task lands.

The same `-Itest/fakes` pattern appears in several sibling on-device
test envs (`nodemcu-32s-multipress-test`, `-serial-test`,
`-profilemanager-test`, `-ble-config-test`, `-leds-test`,
`-gpio2-probe`, `-ble-pairing-test`, `-pin-io-test` — confirm the
exhaustive list in [`platformio.ini`](../../../../platformio.ini)). The
fix should sweep all of them, not just the button env, to avoid the
next on-device test running into the same wall.

## Notes

- **Suspected fix.** The minimal change is to drop `-Itest/fakes` from
  the on-device test envs' `build_flags`: those envs compile real
  Arduino code against a real chip, so the host shim is not just
  unnecessary, it's actively harmful. The header is needed only for
  the CMake-based host build. For the `i_button.h` lookup, verify
  whether the existing `lib_ldf_mode = deep` is enough once the shim
  is out of the way; if not, an explicit `-Ilib/PedalLogic/include`
  may be needed.
- **Out of scope.** Any nRF52840 test env (EPIC-025: hardware
  unreachable). The host `/test` suite. Production firmware envs
  (those already build cleanly). Adding new Unity scenarios — this
  task only restores the build; the scenarios that exist (including
  the two new EPIC-028 ones) should just start working.
- **Why this matters.** Every on-device test env currently shipping
  is unusable today. The button env is the most-affected because
  EPIC-028 added two scenarios to it that depend on a working test
  build, but the same breakage blocks any future on-device test work
  on ESP32. Fixing this once unblocks the whole shape of ESP32 test
  development.
- **Diagnostic shortcut.** The failure is reproducible without
  hardware — just run the build step. Use
  `pio test -e nodemcu-32s-test -f test_buttons_esp32 --without-uploading --without-testing`
  to iterate on the fix without an ESP32 connected.
